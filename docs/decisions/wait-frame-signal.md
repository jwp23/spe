# wait_frame Signal Replaces Settle Sleeps

Decision: Add a `wait_frame` IPC command (PR #134) that blocks until a redraw reflecting every prior command has actually been presented, using a state generation counter compared against a presented-generation counter bumped from `RedrawRequested`, instead of the visual-regression harness's fixed 300ms settle sleep.

Rationale: `App::state_generation` (`src/app/mod.rs`) increments on every `update()` call; `App::presented_generation` is set to match it when `Message::FramePresented` fires, driven by an `iced::event::listen_raw` subscription on `iced::Event::Window(Event::RedrawRequested)` rather than `listen_with`'s normal `event_to_message`, because `RedrawRequested` is broadcast to subscriptions *before* the frame is presented and needs to be observed at that raw stage to mean anything. This subscription is gated to only run while a `wait_frame` is pending (`pending_frame_wait.is_some()`) — subscribing unconditionally would turn every `RedrawRequested` into a `FramePresented` message and never let the event loop go idle, since Iced's `AboutToWait` handler unconditionally requests another redraw whenever the message queue was non-empty.

`wait_frame` targets `state_generation` as of the command *before* it (`saturating_sub(1)`), not its own bump, deliberately giving idle-resolve semantics rather than always paying for one redraw round-trip: if the preceding command's frame is already presented, `wait_frame` returns immediately. This was verified as safe, not just convenient — a self-inclusive target would not hang (the same unconditional-redraw-on-nonempty-queue behavior guarantees `wait_frame`'s own bump gets a follow-up `RedrawRequested` too), and was measured empirically against the running app to resolve in about the same order of magnitude either way (~20ms). A staleness audit found one real gap in this idle-resolve model — `wait_ready`'s zoom handling could report idle before a debounced re-render actually completed — filed and fixed separately (spe-3vp). What remains unaddressed is the compositor/`grim` gap beyond wgpu's own `present()`: `wait_frame` guarantees a frame was submitted to the compositor, not that a screenshot tool reading the compositor's output afterward sees it, though determinism testing (5/5 pixel-identical captures vs. 3/5 for the sleep) shows this residual gap is small in practice.

`wait_frame` supersedes the fixed settle sleep for visual-regression capture: the sleep was both slower than necessary in the common case and not reliably long enough in the worst case, which is exactly the shape of problem an explicit generation-based signal fixes.
