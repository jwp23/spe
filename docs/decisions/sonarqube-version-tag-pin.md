# Sonarqube Action Pinned by Version Tag

Decision: Pin `SonarSource/sonarqube-scan-action` by version tag (`@v8`) rather than by commit SHA. This is the sole intentional exception to the policy of SHA-pinning every GitHub Action.

Rationale: A 40-character hex commit SHA placed next to the word "sonarqube" matches Semgrep's `generic.secrets.security.detected-sonarqube-docs-api-key` detector, which reports a false-positive "SonarQube Docs API Key detected" finding and fails the Semgrep PRO code-scanning check. The flagged value is a commit SHA, not a token. Inline `nosemgrep` suppression proved unreliable against the PRO secrets engine — rule-id-scoped directives did not match its internal rule id, and `nosemgrep` placement support differs between the scanner's container version and newer releases. Pinning by version tag removes the hex string entirely, eliminating the false positive with no suppression needed. Dependabot continues to track the action by tag, exactly as it did at `@v7`.

Trade-off: A version tag is mutable — a compromised upstream tag could be repointed to malicious code, which a SHA pin would prevent. We accept that small supply-chain risk for this single, well-known SonarSource action because the alternative (a SHA pin plus fragile per-scan suppression) is both noisier and less reliable. Revisit and return to a SHA pin if Semgrep gains dependable inline suppression for the PRO secrets engine or the rule is tuned. Tracked in spe-uu3.

## Re-check (2026-08-08, spe-uu3)

Re-verified both open loose ends from PR #98 before closing out this round of triage:

- **Inline `nosemgrep` suppression for the PRO secrets engine**: Semgrep's own docs (docs.semgrep.dev) still call out that Secrets scanning behaves differently from Code/Supply-Chain scanning — for example it ignores `.semgrepignore` entirely — and nothing in the current docs or 2026 release notes documents rule-id-scoped `nosemgrep` support against the PRO secrets engine specifically. The only persistent suppression path found is triaging a finding as a false positive in the Semgrep Cloud/AppSec Platform findings dashboard, which is a per-finding UI action, not an in-repo `.semgrep` config file we could check in. No `.semgrep` config mechanism was found that tunes or disables a single generic secrets rule (e.g. `generic.secrets.security.detected-sonarqube-docs-api-key`) without excluding the whole file from secrets scanning, which we don't want (it would blind the file to real leaked secrets). Conclusion: still not actionable. Keep the version-tag pin and this decision as-is. Re-check again if Semgrep publishes rule-id suppression support for the Secrets engine.
- **`semgrep/semgrep` container image can't be tracked by Dependabot**: [dependabot-core#5819](https://github.com/dependabot/dependabot-core/issues/5819) ("Update `container` image references in GitHub Action workflows") is still open, unassigned, with no linked PR — the `docker` ecosystem still does not cover `container: image:` references in workflow files. No trackable alternative exists. Manual bumping remains the only option. The pinned tag was stale (`1.168.0`, released 2026-06-24) against current upstream (`1.172.0`, released 2026-07-28); bumped to `1.172.0` in `.github/workflows/semgrep.yml` as part of this triage.

  Following Joe's standing SHA-pin-everything policy, the image is now digest-pinned in `tag@digest` form: `semgrep/semgrep:1.172.0@sha256:65dcd4408adda7c183a6b4550cb1e9b19f7f627a6fbb7e0559bd466bedc44d7b`. The digest was resolved from the Docker Hub registry API (`GET /v2/repositories/semgrep/semgrep/tags/1.172.0`) and cross-checked with a direct `GET /v2/semgrep/semgrep/manifests/1.172.0` call against `registry-1.docker.io` requesting `application/vnd.oci.image.index.v1+json` — both returned the same digest, and the response's `media_type`/`Docker-Content-Digest` confirm it is the multi-arch manifest-list (index) digest, not a single-arch image digest. The tag is kept alongside the digest so the version stays human-readable. Because Dependabot can't track this reference at all (per the point above), future manual bumps must update both the tag and the digest together — bumping only the tag would silently repin to the old digest's image.
